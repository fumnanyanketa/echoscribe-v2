## The secret sweep, in detail

The user asked for key material specifically, in the repository and its
history. This is what was done and what it found.

**Nothing was found. No key, token, password or private key exists in the
working tree or in any of the 56 commits.**

- Every keyword hit for `api key`, `secret`, `password`, `token`,
  `authorization` and `BEGIN PRIVATE KEY` across `git log -p --all` was
  read. Every one is prose: design-system colour "tokens", Deepgram's 500
  **token** request limit, the password-field refusal, and today's review
  file. One test fixture contains the literal string "the secret plan",
  which is a search-test payload in `history/store.rs`, not a secret.
- **Deepgram key shapes.** Deepgram keys are 40 hexadecimal characters.
  All 56 unique 40-hex strings in the entire history were extracted and
  each one was tested with `git cat-file -e`. **All 56 are git object
  SHAs.** None is key material.
- **Other vendor shapes**: `sk_`/`pk_`/`rk_` live and test keys, Google
  `AIza`, GitHub `ghp_`, Slack `xox*`, AWS `AKIA`, and JWTs. Zero hits
  across all history.
- **High-entropy strings**: every alphanumeric run of 24 characters or
  more in every tracked text file was extracted and reviewed. All are npm
  integrity hashes in `package-lock.json` or documentation URL slugs.
- **No `.env` file has ever been committed.** `.gitignore` has covered
  `.env` and `.env.*` since before the sign-in feature was built, which
  was deliberate. The only file ever deleted from history is two starter
  SVG icons.
- **No Clerk secret key exists anywhere.** The app ships
  `OAUTH_CLIENT_ID`, which is a public OAuth client identifier and is
  meant to be public. That matches record 0003's refusal to ship a secret
  key.

**On the Deepgram key that once reached a session log through a Notepad
window title**: that leak was into a conversation transcript, outside this
repository. This sweep confirms **it never reached the repository or its
history**. Nothing here needs rotating on account of anything found in
git. Whether that key was rotated after the original incident is outside
what this sweep can see, and if it was not, it should be: a key that ever
appeared in a log is a leaked key, and deleting the log does not undo it.

## The personal data finding, in full

This is the one that matters, and it is worth being precise about.

`docs/evidence/the-app-shell/` holds 12 PNGs, committed in `2853a65` and
`9262a9f`. Three are full-desktop captures at 3840x2160. Two were opened
and read directly during this sweep.

**What is actually visible**, confirmed by looking, not inferred:

- **Full name and personal email address**: "fumnanya nketa" and a
  personal `@gmail.com` address, rendered by the app's own account block.
  Confirmed in `AC-6-3-small-window-hidden-dashboard-revealed-unraised.png`
  and in `AC-1-dashboard-at-rest.png`.
- **The Windows user path**, `C:\Users\fumna\dev\echoscribe-v2`, in a
  terminal window.
- **The desktop wallpaper**, a personal image of a person.
- **A full software inventory** from the desktop icons: AnyDesk, Brave,
  Chrome, Edge, OBS, Notion, Anki, Audacity, DaVinci Resolve, CapCut, the
  Adobe suite, two Claude apps and an IDE. A list of what is installed on
  a machine is reconnaissance.
- **Private project names** in desktop filenames: "lead-gen-backup-p...",
  "africa-week-brand-...", "africa-week-flyer-m...", "GodTierSprint",
  "BuildersPlaybook".
- **Locale and local time**: ENG US, a weather widget reading 16C, and
  timestamps of 12:32 and 12:35 on 3 September 2026.

**One correction to the brief.** The user described four full-desktop
screenshots. The exposure is wider than that. The account block is part of
the dashboard, so **the name and the personal email appear in the cropped,
window-only screenshots too**, not just the full-desktop ones.
`AC-1-dashboard-at-rest.png` is 59 KB and shows the window alone, and it
carries the name and the email plainly. Any screenshot in this folder that
includes the dashboard's left rail carries them. Two of the twelve were
opened and confirmed; the rest were not opened individually, so treat the
whole folder as suspect rather than trusting a per-file list.

**What someone could do with it**: learn who the author is, reach them at
a personal address, know what software to target, and know roughly where
and when they work. It is a phishing and social-engineering foundation
rather than an immediate compromise.

**Why it is High and not Critical**: `git remote -v` is empty. This
repository has never been pushed anywhere. Nobody outside this machine has
a copy, so nothing has leaked yet.

**Why it still matters, and the part that is unintuitive**: deleting the
files in a new commit **does not fix this**. The images stay in history,
and anyone who clones the repository after it is published gets every one
of them. The only real fix is rewriting history, and that has to happen
**before the first push, not after**. Once it is pushed, it is out.

This is a decision for the user, not for this skill: the images are
genuine verify evidence and deleting them costs something. The options are
to rewrite history and re-capture cropped evidence, to keep the repository
private forever, or to accept the exposure knowingly. Nothing was changed
here.

## Promised but not built

Record 0002 and record 0003 each name refusals the system must honour.
Each was checked against the code. **Every refusal that can be checked by
reading code is genuinely built**, and several are enforced structurally
rather than by good intentions. That is a better result than this section
usually gets.

**Built, and verified this run:**

- **The hook is not a keylogger.** Record 0002 calls this the single most
  dangerous thing in the feature. `hook.rs:122-156` reads only the virtual
  key code and the up/down flag, immediately collapses the key to a
  two-valued `Class` (`Modifier` or `Other`), and drops the code. Nothing
  is stored, buffered, accumulated or compared against anything but the
  four modifier keys, and every event is passed on with
  `CallNextHookEx`. The refusal is built exactly as written.
- **No audio is ever written to disk.** Enforced by source guards in
  `microphone.rs:815`, `transcribe.rs:752` and `typing.rs:357`, which fail
  the build if `std::fs`, `File::`, `OpenOptions` or `BufWriter` ever
  appear in those files. `typing.rs` also forbids `reqwest`.
- **Nothing writes to a Windows privacy setting.** Guards in
  `consent.rs:157-160` and `sound.rs:435-438` fail the build on
  `RegSetValue`, `RegCreateKey`, `RegDeleteKey` or `RegDeleteValue`. Only
  `RegGetValueW` reads appear.
- **The Deepgram key is never shown in full after saving.** Only
  `last_four` is stored in the database and only `last_four` crosses into
  the interface (`deepgram_key.rs:281-286`, `324-334`). The key itself
  goes to Windows Credential Manager.
- **Only fixed outside addresses can be opened.** `open_fixed_page`
  (`deepgram_key.rs:509`) takes a `&'static str`, so a runtime-built URL
  cannot reach it at all. The type system enforces the refusal. It also
  refuses when nobody is signed in. Clerk URLs are all built from one
  fixed `CLERK_DOMAIN` constant.
- **No token or email reaches a log.** Every one of roughly 50 `eprintln!`
  lines was read. The two that print a token-endpoint failure use
  `oauth2`'s error response type, whose `Debug` is the error code,
  description and URI only, and the code says so in a comment. Better:
  `RequestTokenError::Parse(e, _raw)` at `clerk.rs:312` **deliberately
  discards the raw body**, with the comment "a success body would contain
  tokens". That is someone thinking about exactly the right thing.
- **No command can reach another account's data.** Every one of the 23
  Tauri commands was listed. **Not one takes an account id from the
  interface.** Each derives it from Rust's own session state via
  `account_id_from(app)`. `remove_vocabulary_term` takes a row id, and
  there is a test named `one_account_cannot_remove_anothers_word` holding
  that door. There is no IDOR here.
- **PKCE, state and the loopback listener.** `handoff.rs:64` binds
  `127.0.0.1:0`, a random free port on the loopback interface only, never
  a public one. The state value is checked before the code is trusted and
  a mismatch is refused and logged.
- **No Clerk secret key is shipped.** The app is a public OAuth client, as
  the record requires.

**Cannot be checked by reading code, and therefore not confirmed:**

- **"Open the microphone without the pill being visible."** Needs a live
  run.
- **"Let the pill take focus."** Needs a live run, and today's
  `/check review` raises a specific doubt: the child-window walk in
  `pill_mouse.rs:90-104` only visits direct children, while WebView2 nests
  deeper, and the test proves one level only.
- **"Keep showing an error the person has already fixed."** The clearing
  table is rule 16's shape and only a live run settles whether it clears
  on proof rather than on a timer.

These three are not failures. They are unproven, and they stay unproven
until `/check verify` runs, which it has never successfully done on this
project.

## Clean

Worth saying, because a report that only lists problems misleads.

- No secrets in the code or in any of the 56 commits, by every pattern
  tested.
- No `.env` ever committed; `.gitignore` covered it pre-emptively.
- npm dependencies: 0 vulnerabilities across 12 packages.
- No XSS sink anywhere in the interface: no `innerHTML`,
  `insertAdjacentHTML`, `document.write` or `eval` in any of the eleven
  drawing files, despite several screens rendering hostile input by
  design.
- Every SQL query is parameterised and account-scoped. `history/store.rs`
  binds a literal SQL-injection string in its own tests to prove it.
- Every `.unwrap()` in the Rust core is inside a `#[cfg(test)]` module.
  Production paths have none.
- The loopback OAuth listener binds only `127.0.0.1` on a random port.
- All Clerk and Deepgram traffic is HTTPS to fixed domains.
- No `unsafe` block hides a secret: all 50 are Windows API calls, reviewed
  today by `/check review` for their return-value handling.

## What blocks what

Critical findings. `/liftoff` is not blocked by this report.

**Two things gate a release when one is attempted**, and both should be
fixed first rather than argued about later:

1. **Clerk must move from its development instance to a production one.**
   Real people's sign-in should not run on `clerk.accounts.dev`.

**One thing blocks publishing this repository**, which is not the same as
releasing the app:

3. **The personal data in `docs/evidence/the-app-shell/` must be dealt
   with before the first `git push`, not after.** Deleting the files later
   does not remove them from history.

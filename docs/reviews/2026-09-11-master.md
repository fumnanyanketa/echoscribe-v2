## Summary

The engineering here is careful and unusually well documented. Secrets are
handled properly, SQL is parameterised and account-scoped everywhere, there
is not one XSS sink in the entire interface, and several past bugs have left
behind source-level guards that explain in their own words what a person saw
when the thing broke. That is a real standard.

Against that, one blocker: the application opens two different SQLite files
while every comment in it asserts there is one. Three of the six features
read and write `echoscribe.db` and the other three read and write
`echoscribe.sqlite3`. The tables the first three depend on are created only
in the second file. Records 0005, 0006 and 0007 therefore cannot work on a
real machine, including the screen the app lands on after sign-in. Two
reviewers found this independently and the main thread confirmed it three
ways.

The rest of the findings cluster in one place, and it is the place the seam
question was asked about: timing. A dozen individually correct decisions
meet without anyone having specified who wins. The single largest structural
cause is that no test in this project ever exercises the real startup path
with all six features against one file, which is exactly why the blocker
survived 342 passing tests.

## Blockers

### 🔴 The app opens two different databases, and three features are non-functional as a result

`src-tauri/src/vocabulary/mod.rs:38`, `src-tauri/src/language/mod.rs:36` and
`src-tauri/src/history/mod.rs:34`:

```rust
const DB_FILE: &str = "echoscribe.db";
```

`src-tauri/src/sign_in/mod.rs:31`, `src-tauri/src/dictate/mod.rs:118` and
`src-tauri/src/shell/mod.rs:41`:

```rust
const DB_FILE: &str = "echoscribe.sqlite3";
```

All six join their constant to the same `app.path().app_data_dir()`. These
are two different files on disk.

**Problem**: The `account` table is created only in `sign_in/store.rs:28`
and the `dictation` table only in `dictate/store.rs:159`. Both of those open
`echoscribe.sqlite3`. The three features that open `echoscribe.db` depend on
tables that are never created there.

Traced, and confirmed by the main thread against the source:

- **History cannot read.** `history/store.rs:82`'s `open` deliberately
  creates nothing, on the documented assumption that dictate has already
  created `dictation`, "which is what the init order in `lib.rs` is for". In
  `echoscribe.db` that table never exists, so `page()`'s
  `SELECT ... FROM dictation` (`history/store.rs:112`) fails on every call.
  `get_history` maps it to `HISTORY_NOT_READ`, "Your history could not be
  read, so none of it is shown." History is record 0004's landing
  destination, so **this is the first thing every signed-in person sees on
  every launch, forever**.
- **Vocabulary cannot save.** `vocabulary/store.rs:62` sets
  `PRAGMA foreign_keys = ON` and the table carries `REFERENCES account(id)`.
  `CREATE TABLE` succeeds, because SQLite does not resolve a `REFERENCES`
  target at creation time, so `get_vocabulary` returns an empty list quite
  happily. Every `add_vocabulary_term` fails against a parent table that
  does not exist in that file, and the person reads "This could not be
  saved, so your list is unchanged." every single time, with no way to ever
  add a word.
- **Language cannot save**, identically. `language/store.rs:49` sets the
  same pragma. `get_transcription_language` always reports the English
  default and `set_transcription_language` always returns "This language
  could not be saved, so it is unchanged."

The prose makes this worse rather than better. `history/mod.rs:32-33` reads
"The same file every other feature opens" directly above the wrong name.
`vocabulary/store.rs:5-8` and `lib.rs:20-24` both assert the same thing.

**Why it matters**: Three of the five features on the plan are unusable, and
one of them is the app's landing screen. It reproduces on first launch, for
every person, every time. It also breaks the AGENTS.md data rule that all
persistent data lives in one SQLite file on the person's machine: today it
lives in two.

**Why no test caught it**: every store test opens an in-memory database or
its own throwaway temp file and hand-creates the `account` table inside the
same connection under test. Nothing in `cargo test` runs `lib.rs`'s real
startup, with all six `init` functions, against one real path. The suite
proves each feature works against a file shaped the way that feature
imagines, which is not the file it gets.

**Suggested fix**: one constant, used by all six. `echoscribe.sqlite3` is
the name to keep, since it is the one the `account` and `dictation` tables
already live in and the one any existing installation has data in. Then an
integration test that runs the six `init`s in `lib.rs`'s own order against a
single temp directory and asserts every table exists afterward in the one
file. Note that choosing where a shared constant lives is an `/architect`
decision under the feature-folder rules, and that AGENTS.md already records
an owed extraction in this same shape.

## Major

### 🟠 A token refresh landing after sign-out can resurrect the deleted credential

`src-tauri/src/sign_in/renewal.rs:41-108`. `tick()` runs on a 60 second
loop. It reads the session and loads the tokens (line 58), then calls
`clerk::refresh_tokens` (line 79), a network call with a 15 second timeout.
`sign_out` (`sign_in/mod.rs:187-198`, via `clear_local_session` at 99-110)
can run during that window, deleting the Credential Manager entry and
clearing the session row.

When the refresh then completes,
`credentials::store(&session.credential_target, &fresh)` at `renewal.rs:81`
writes a **new** Credential Manager entry under the old account's target,
holding a fresh valid refresh token for an account nobody is signed into.
`announce_signed_in` (`renewal.rs:124-132`) then emits `auth:signed_in` for
that account.

**The author knew about this race and guarded the other half of it.**
`store.rs:229-231`'s doc comment on `mark_verified` says it touches the row
"only while somebody is signed in, so a refresh landing after a sign-out
cannot revive a dead session", and the SQL carries
`WHERE id = 1 AND account_id IS NOT NULL AND account_id <> ''`. The database
write is guarded. The Credential Manager write three lines earlier is not.

**Why it matters**: record 0003's data rules say signing out deletes the
Credential Manager entry. A signed-out account's refresh token can end up
alive again on the machine, orphaned, never referenced or cleaned up. That
is a real credential outliving its session.

**Suggested fix**: re-read the session row and confirm `account_id` still
matches the account this tick started with, immediately before the
`credentials::store` call and the announce. The guard already exists one
function away; apply the same one here.

### 🟠 A non-BMP character can still be split across two `SendInput` calls

`src-tauri/src/dictate/typing.rs:174-188`. `send()` collects
`text.encode_utf16()` into `units` and iterates `units.chunks(BATCH)` with
`BATCH = 8` (`typing.rs:69`), one `SendInput` per chunk with a
`std::thread::sleep` between them. A surrogate pair that lands on a chunk
boundary has its two halves sent in separate calls with the input queue open
in between.

This is the known bug in
`docs/evidence/dictate-with-a-hotkey/finding-non-bmp-character-split-across-batches.md`,
found 2026-08-30 against `BATCH = 32`, left unfixed and routed to plan row 4
as its owner. Row 4 shipped on 2026-09-04 and fixed key-code derivation, not
this. `BATCH` shrinking from 32 to 8 on 2026-08-31 means more boundaries per
phrase, not fewer.

The comment at `typing.rs:170-172` says a character outside the basic range
"arrives as two units and is sent as two, in order, which is what Windows
expects". That is true inside one call, and is probably why the boundary
case survived.

**Why it matters**: accuracy is the one thing this app must do well, and
record 0006 has now shipped the multilingual support that makes rare scripts
and emoji reachable. A corrupted character lands silently in the person's
document.

**Suggested fix**: group on `char` boundaries into runs under `BATCH`
UTF-16 units, so a pair can never straddle two calls. This is what the
evidence file itself prescribes.

### 🟠 No timeout on the Deepgram connect, and it can stall the one command thread

`src-tauri/src/dictate/transcribe.rs:428-444` and `452-485`. `connect()`
calls into the `deepgram` crate, which calls
`tokio_tungstenite::connect_async` with no timeout. `reconnect()`'s
`while Instant::now() < deadline` bounds how many times the loop is
**entered**, not how long one attempt takes, so a single connect can hang
far past the 5 second `RECONNECT_WINDOW`, bounded only by OS TCP and DNS
timeouts. `run()`'s first connection at line 286 has the same gap.

It compounds: `Session::stop()` (`transcribe.rs:176-182`) joins the worker
and blocks, and `Live::close()` (`dictate/mod.rs:186-197`) calls it from the
single `echoscribe-dictate-commands` consumer thread, which processes every
command serially by design. A hung connect blocks that thread, so the double
tap that would stop the dictation sits unprocessed until the hang clears.

**Why it matters**: AC-5 and AC-14 both promise bounded endings. This is
standing rule 14's shape applied to timing: a budget the record states and
nothing in the code enforces per attempt.

**Suggested fix**: wrap each connect in `tokio::time::timeout`, in both
`run()` and `reconnect()`, well under `RECONNECT_WINDOW`.

### 🟠 The password check and the typing target are read three times, through two different Windows subsystems

`src-tauri/src/dictate/typing.rs:114-137`, `148-166` and `215-236`.
`type_at_cursor()` calls `focused_field_is_a_password()` (UI Automation's
`GetFocusedElement` and `CurrentIsPassword`), then
`focused_window_collapses_injected_keystrokes()` (its own fresh
`GetForegroundWindow`), then `focused_text_box()` (a third query, using
`GetForegroundWindow` plus `GetGUIThreadInfo`). `send()` posts through
`SendInput` to whatever is foreground at the instant of the call.

Nothing pins these readings to the same element. Focus moving in the gap
means the check can pass on one field while the characters land in another.

**Why it matters**: AC-20 treats "never type into a password field" as
absolute, and this is one of the four worst cases named in the record's Risk
section.

**Suggested fix**: resolve the focused element once per phrase and derive
both the password check and the typing target from that single reading.

### 🟠 Window show, hide and focus never check that the effect landed

`src-tauri/src/dictate/mod.rs:634-640`:

```rust
fn bring_window_forward(app: &AppHandle) {
    if let Some(window) = app.get_webview_window("main") {
        let _ = window.show();
        let _ = window.unminimize();
        let _ = window.set_focus();
    }
}
```

All three Results are discarded. The same at `pill_window.rs:144` and
`pill_window.rs:172`.

This function is the only delivery mechanism for AC-9, AC-13, AC-15, AC-28,
AC-29, AC-30 and AC-32. If it silently fails, the person is told nothing at
all about why dictation refused to start.

This is standing rule 17's exact shape, in a codebase where that rule exists
because the bug has already shipped twice. `pill_window.rs:150-158` already
applies the right discipline a few lines above, so the pattern is known.

**Suggested fix**: check `is_visible()` and `is_focused()` afterwards and
log loudly when the expected state was not reached.

### 🟠 A third path shows the "main" window outside shell's one tested gate

`src-tauri/src/dictate/mod.rs:634-640` versus
`src-tauri/src/shell/mod.rs:277-302`. Shell proves by source guard that
exactly one function **hides** the small window and that it always checks
whether a dashboard exists first, because two windowless bugs shipped from
getting exactly that wrong. Nothing symmetrical exists for **showing** it.
`bring_window_forward` shows, unminimises and focuses `"main"` directly,
from two call sites (`mod.rs:628` and `mod.rs:917`), with no call into
`shell::settle` and no check of `shell::dashboard_is_due`.

The two features stay in step only because dictate also emits
`dictation:error` and `dictation:needs_key`, which shell listens for and
uses to update its `interruption` mutex, read only on the **next** settle.
Nothing enforces that shell's state is updated before the window dictate
just forced into view is what a person is looking at.

**Suggested fix**: either route this through shell's own gate, which is a
cross-feature-import decision and therefore `/architect`'s, or give showing
the same source guard hiding already has.

### 🟠 Six connections to one file, with no busy timeout and no journal mode

`sign_in/store.rs:78`, `dictate/store.rs:130`, `shell/store.rs:54`,
`vocabulary/store.rs:46`, `language/store.rs:33` and `history/store.rs:82`
each open their own `Connection` behind their own `Mutex`. That serialises
writes within a feature and not at all across features. The only pragma set
anywhere is `foreign_keys = ON`; `busy_timeout` and `journal_mode` appear
nowhere in the codebase, confirmed by grep.

SQLite's default busy timeout is 0 ms, so two features writing at once, for
instance shell's geometry write and dictate's history write, can get
`SQLITE_BUSY`. Every writer here logs and drops it
(`dictate/mod.rs:513-515`, `shell/mod.rs:360-362`). On sign-in's own
three-write path (`sign_in/mod.rs:261-291`) a busy error would surface to
the person as a failed sign-in blamed on Clerk.

**Suggested fix**: set `PRAGMA busy_timeout` on every connection, from
wherever the shared file constant ends up living. Consider WAL.

### 🟠 A hotkey press queued at sign-out can open the microphone under a signed-out account

`src-tauri/src/dictate/mod.rs:267-271`. The `auth:signed_out` listener calls
`hook::disarm()`, which stops only future presses, and `close_if_listening`.
Neither touches a `try_start` already in flight. `try_start`
(`mod.rs:368-494`) holds the `listening` mutex from before
`microphone::open()` all the way through `*listening = Some(Live{...})` at
line 483, across a real hardware open and a Deepgram connect.
`close_if_listening` blocks on that same mutex until it finishes, and then
tears down what was just opened.

In the meantime the microphone genuinely opens, the pill appears, the open
sound plays, and `Live.account_id` holds the account that has just signed
out. Audio can be captured and streamed to Deepgram under that account's
key.

**Suggested fix**: have `try_start` re-check that its captured account is
still signed in immediately before committing `*listening`, and tear the
microphone back down if not.

### 🟠 The silence cap and a dying microphone race for who ends the dictation

`src-tauri/src/dictate/mod.rs:553-583`, `limits.rs:80-88` and
`microphone.rs:399-422`. The level thread ticks every 60 ms and sends
`Command::CloseBecause("silence")` when the deadline passes. The cpal error
callback sends `Command::DeviceDied` the instant a real failure arrives.
They are idempotent against each other, so nothing tears down twice, but
there is no ordering guarantee.

Record 0002 is explicit that this must not happen: "The silence cap must not
get there first... The device failure ends the dictation the moment the
stream reports it, and the cap is left for the thing it is for." Nothing in
the code enforces that priority. It holds because `DeviceDied` is usually
faster than a 60 ms poll, which is true nearly always and guaranteed never.

Whichever send lands first decides whether the person sees MIC STOPPED with
a cause, or the pill simply vanishing with no explanation.

**Suggested fix**: give `DeviceDied` unconditional priority through a flag
the silence check consults before acting on an expired deadline.

### 🟠 Replace and Remove on the Deepgram key can race, resurrecting a removed key

`src-tauri/src/dictate/deepgram_key.rs:353-403` and `457-491`. Neither
command locks per account. `save_deepgram_key` does a network round trip of
up to 10 seconds before it writes; `clear_deepgram_key` deletes the row,
emits, then deletes the vault entry. A Remove that completes while an
earlier Replace is still in flight lets Replace's write land afterwards
under the same deterministic target name, putting the key back with no event
telling the shell to redraw.

AC-35 says Remove means the key is gone from the machine and that backing
out changes nothing. A resurrected key is neither state.

**Suggested fix**: serialise writes to one account's key, with a per-account
mutex or a generation check.

### 🟠 Vocabulary terms reach Deepgram with no awareness of the chosen language

`src-tauri/src/dictate/mod.rs:412-413`, `vocabulary/mod.rs:274-289` and
`language/mod.rs:195-209`. `try_start` reads `language_for_dictation` and
`terms_for_dictation` independently, and neither function, nor
`vocabulary::rules::sendable`, has any concept of the other.

A person can build an English vocabulary list, switch transcription to
Japanese or to "multi", and the next dictation sends the unfiltered English
keyterm list alongside a non-English stream. Nothing in this codebase checks
whether Deepgram honours, ignores or rejects keyterms outside the supported
languages for the model in use.

This is the case AGENTS.md's own "things to know" section flags as unproven,
and it needs a live check against Deepgram rather than a guess. Record 0005
and record 0006 each specify their own half and neither specifies the pair.

### 🟠 `main.js` registers its event listeners without awaiting them

`src/main.js:110-245` registers eight listeners, none awaited, then calls
`render()` at line 247. `src/shell/dashboard.js:64-78` explicitly awaits its
two `listen(...)` calls before invoking anything, and says why in place:
"Proved live on 2026-09-03, where exactly that happened."

Textual ordering is what dashboard.js had before it was fixed. This is the
bug class standing rule 17 names by example, in the one file that rule was
written about. The window is narrow, first load only, but the events
involved are exactly the ones this window exists to catch.

**Suggested fix**: await every `listen(...)` before `render()`, matching
dashboard.js.

## Seams

The seam question was asked of every reviewer by name. This is the category
the author structurally cannot see, and it is where most of this review
landed.

**Specified and held.** Two crossings that were most likely to break are
correct and proven by source guards: a setting changing mid-dictation
(`dictate/mod.rs:979-1062`) and two ending paths firing at once
(`language/mod.rs:420-435`). Every ending converges on one
`Mutex<Option<Live>>` taken with `.take()`, which makes the ending
idempotent by construction rather than by care. Sign-out and a failed
background refresh converge on the same event and the same pattern.

**Unspecified, and each one is a finding above.**

1. **Six `const DB_FILE` literals.** The folder-isolation rule is exactly
   why each feature declares its own, and applying that rule six times with
   a bare string literal is what let three drift. Every feature's tests use
   throwaway files, so the shared path is never exercised. This seam
   produced the blocker.
2. **Silent renewal against sign-out.** The database write is guarded, the
   Credential Manager write beside it is not.
3. **The silence cap against a dying microphone.** The record names a
   winner; the code does not enforce one.
4. **`retry_dictation` is a second, unserialised door into `try_start`.**
   The hotkey path is serialised through one channel and one thread, and the
   code's comments lean on that for correctness. This one steps outside it,
   protected only by the mutex and by UI timing lining up today.
5. **Sign-out disarms the hook, not an in-flight `try_start`.**
6. **Showing the main window against shell's gate for hiding it.** Guarded
   in one direction, unguarded in the other.
7. **Replace against Remove on the Deepgram key**, across a network round
   trip, with no ordering rule.
8. **The password check against the typing target**, two Windows subsystems
   and three instants per phrase.
9. **The five second reconnect budget against the single command consumer.**
   Each is fine alone. Nobody specified what happens when the first
   overruns, and the second's liveness depends on it not doing so.
10. **Vocabulary terms against the chosen language**, two records each
    specifying their own half.
11. **`dictation:opened` means two things at once.** It is a "just started"
    signal and a clearing signal for the microphone error family only. A
    hotkey press queued during the two second hold after a *Deepgram* family
    error opens a new dictation and broadcasts `dictation:opened`, which
    clears nothing in that family. A fresh dictation then runs, pill and
    all, while the EchoScribe window still shows the stale Deepgram error
    from the previous one.

**Known and accepted, worth writing down.** `dictation:text` broadcasts to
every window rather than only the pill (`transcribe.rs:607-614`),
deliberately, so the clearing table can hear that the allowance is back. It
is reasoned and documented. It does mean every current and future window
receives live transcript text on the event bus.

## Strengths

These are genuine and worth keeping.

- **Not one XSS sink in the entire interface.** No `innerHTML`, no
  `insertAdjacentHTML`, no `document.write`, no `eval` anywhere in `src/`,
  confirmed by the main thread across all eleven drawing files, despite
  several screens rendering hostile input by design. Every screen builds
  nodes and sets `textContent`.
- **The key is clean.** It appears in no `Debug`, log line, event payload or
  command return anywhere in the dictate feature. The source guards scan the
  whole file rather than a line prefix, explicitly because a prefix scan was
  once defeated.
- **Every `.unwrap()` in the Rust core is inside a `#[cfg(test)]` module.**
  The main thread checked all six of the heaviest files: production paths
  have none.
- **Per-account SQL scoping is uniformly correct**, and `history/store.rs`'s
  tests bind a literal SQL injection string to prove parameter binding
  holds.
- **The rule 15 split in `microphone.rs` is exactly right**, and backed by
  measured live evidence rather than a plausible assumption: 88 `Xrun`
  reports in 35 seconds under load, with 1.4 million frames still delivered
  after the first one.
- **`sound.rs` and `consent.rs` both generalise the rule 14 lesson
  correctly**, checking the scheme entry and the file's existence before
  trusting `PlaySoundW`, and treating an unreadable registry switch as not
  evidence in either direction.
- **Past bugs left behind guards that explain themselves.** `shell/mod.rs`
  carries five source-level guards, each tied to a specific named bug that
  actually shipped, written in terms of what a person saw. That is unusually
  good practice.
- **OAuth PKCE is correct in the details that usually go wrong**: state
  checked before the code is trusted, an ephemeral loopback port, verifier
  and state held in memory only, and "Clerk refused" kept distinct from
  "Clerk unreachable" by dedicated tests.
